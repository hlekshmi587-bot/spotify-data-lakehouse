# Global Spotify Music Data Engineering - Analytical Model, dbt & SQL Analytics
### Member 3 module: star schema, dbt transformations, SQL analytics

This folder adds the **analytical layer** on top of Member 2's Bronze-Silver-Gold lakehouse:

| Responsibility | Where it is implemented |
|---|---|
| Design the analytical data model (fact / dimension tables) | `models/marts/core/`, `docs/data_model.md` |
| dbt transformations | `models/staging/`, `models/marts/`, `macros/` |
| SQL analytics (regional, temporal, seasonal, genre, artist patterns) | `models/marts/analytics/` (marts) and `analyses/` (12 ad-hoc queries) |
| Quality checks on the model | 102 dbt tests (`*.yml`, `tests/`), incl. reconciliation with Member 2's Gold |

## 1. How it fits the pipeline
```
raw CSV -> Bronze -> Silver -> Gold (Parquet)          Member 2  (PySpark)
                       |         |
                       +---------+--> dbt + DuckDB      Member 3  (this folder)
                                         staging -> core (star schema) -> analytics marts
                                                         |
                  Member 4: `dbt build` as an Airflow task + Great Expectations on Gold/Silver
                  Member 5: exports/*.parquet or target/spotify_warehouse.duckdb -> dashboard
```
**Why dbt-duckdb and not dbt-spark?** The lakehouse is a set of local Parquet files. DuckDB reads them in place
(no copy, no Spark Thrift server, no Hadoop/`winutils` problem on Windows) and runs standard SQL, so the whole
project builds in ~5 seconds. The SQL is ordinary ANSI-style; moving to Spark/Databricks later means changing the
adapter and a few DuckDB functions (`generate_series`, `unnest`, list lambdas).

## 3. Installation
Python 3.10+ (tested with 3.12). No Java or Spark is needed for this module.
```bash
cd dbt_spotify
python3 -m venv .venv && source .venv/bin/activate        # Windows PowerShell: py -3.12 -m venv .venv ; .\.venv\Scripts\Activate.ps1
pip install -r requirements.txt
```

## 4. Running
Member 2's Parquet files must exist (run `python -m spark.run_pipeline` in `spotify-data-engineering/` first).
By default dbt looks for them in `../spotify-data-engineering/data` (this folder next to Member 2's). Otherwise set the path:
```bash
export SPOTIFY_DATA_DIR=/path/to/spotify-data-engineering/data        # PowerShell: $env:SPOTIFY_DATA_DIR = "C:/dev/spotify-data-engineering/data"
dbt build                          # staging -> star schema -> marts, and ALL tests   (exit code 0 = everything passed)
dbt compile                        # compiles analyses/ (needed once before run_analyses.py)
python scripts/run_analyses.py     # runs the 12 queries and writes docs/sql_analytics_results.md
python scripts/export_marts.py     # writes exports/ (Parquet) for the dashboard
dbt docs generate && dbt docs serve   # optional: browsable lineage graph and column docs
```
Run `dbt` from inside `dbt_spotify/` (it finds `profiles.yml` in the current folder). The warehouse is `target/spotify_warehouse.duckdb`
(override with `DBT_DUCKDB_PATH`).

## 6. Read this before using any number (data limits)
1. **Audio features exist for only 17.11% of chart rows** (tracks present in `tracks.csv`). Audio/genre/mood results describe that subset;
   marts carry `matched_entries` / `track_attribute_coverage` so this stays visible.
2. **The chart file is a thin sample**: 99.9% of Top 200 rows come from 7 dates (Jan-Feb 2017 and Mar 2018); Viral 50 has 22 rows.
   Therefore **"Winter" is essentially 2017 and "Spring" essentially 2018 - season and year cannot be separated.** Summer and Autumn
   have too few rows to analyse. Trend marts include a `data_volume` flag (`ok` / `limited` / `insufficient`). The seasonal and
   temporal marts demonstrate the method; they do not prove a seasonal effect.
3. `streams` are sums over the sampled days, not lifetime totals.
4. No artist ids in the sources -> artists are identified by name only.

## 7. Interfaces for the other members
* **Member 4 (Great Expectations + Airflow):** call `dbt build` as a task (exit code 0 / non-zero). dbt tests cover model-level rules
  (keys, relationships, ranges, reconciliation); Great Expectations can cover the raw/Silver/Gold files themselves - the two are complementary.
* **Member 5 (dashboard):** read `exports/analytics/*.parquet` (ready-made marts) and `exports/core/*.parquet` (star schema) with
  pandas/DuckDB/Power BI, or connect to `target/spotify_warehouse.duckdb`. Use `mart_country_profile` for maps, `mart_genre_performance`,
  `mart_artist_leaderboard`, `mart_country_top_tracks`, `mart_period_trends`. Filter `is_global = false` when comparing countries.

## 8. Limitations and future work
* DuckDB local files only (no Spark/Databricks adapter, no incremental models - the data is small and rebuilt in seconds).
* Surrogate keys are regenerated each build; they are stable for identical input but not across data changes.
* `dim_artist` has no country/genre (not in the sources); same-name artists are merged.
* Mood quadrant and tempo band are conventions, not Spotify fields.
* With a fuller chart history the seasonal marts would become meaningful without model changes.
